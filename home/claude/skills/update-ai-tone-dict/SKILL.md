# AI 文体辞書の更新

`home/textlint/dict` の辞書を育てるスキル。辞書は一度書いて終わりにならない。
使っているうちに「これは誤検出だ」「この言い回しが漏れている」が必ず出てくるので、
そのたびに最小の変更を入れて回帰テストを通す、という作業を繰り返す。

辞書は `dict/ai-tone.yml` の 1 ファイル。フックが同じ辞書を当てるので、
足した規則は会話にも、書いた Markdown にも、GitHub へ投稿する本文にも当たる。

## 更新の流れ

### 1. 何を直すのかを一つに絞る

1 回の更新で扱うのは 1 語（とその変種）か、1 件の誤検出まで。
まとめて入れると、後で誤検出が出たときにどの追加が原因か切り分けられなくなる。

入力源は次のどれか。どれであっても、次のステップの判断基準は同じ。

- ユーザーが「この言い回しは AI っぽい」と指摘した
- textlint の指摘が的外れだった（誤検出）
- 書いた文章を読み返して、明らかな常套句が素通りしていた（見逃し）
- フックの指摘がうるさいとフィードバックが来た

### 2. 辞書に入れるべきか判断する

**削除テスト**を当てる。その語を消して文の命題が変わらないなら、
その語は情報を運んでおらず、長さを稼ぐためだけに存在している。辞書に入れてよい。

消すと意味が変わる語は入れない。`幅広い` は「幅広い層に使われている」から消すと
「層に使われている」になり、広さという主張そのものが落ちる。一度入れて外した語なので、
`from` と `to` を同じにした `specs` が見張りとして辞書に残っている。

ただし「消せない」と「入れない」を同じ意味に取らないこと。`かもしれません` を拾う
「逃げのヘッジ」は、`expected` が「断定するか、根拠を添えて条件を書く」で、
ぼかすこと自体を禁じていない。
書き手に次の一手を二択で示している。**禁止ではなく次の一手を指定できるか**が分かれ目になる。
消せない語で、しかも代わりに何をすればいいかを書けないなら、それは入れない語。

境界線上の語も入れない。出し分けの仕組みが無いので、様子見のつもりで入れる場所が無い。

### 3. 誤検出の見積もりを取ってから書く

パターンを思いついたら、辞書へ書く前に文章へ当てて何件引っかかるかを見る。
手元の実際の記事を使えるならそれが一番いい。

```bash
rg --only-matching --count-matches '<候補パターン>' ~/workspace/**/*.md
```

記事が無いときは検証用のダミー記事を書いて当てる。ここが省かれやすいが、
省くと「書いたパターンが自分の想定どおりに動く」ことしか確かめられない。

**拾いたい形だけを並べたダミーは書かない。** それは必ず全部引っかかるので何も分からない。
落ちてほしい文を混ぜて初めて、パターンが広すぎるかどうかが出る。次の 3 種類を混ぜる。

- 拾いたい形（その語が水増しとして使われている）
- 同じ語が述語や名詞の中身になっている形（削ると本文が壊れる）
- 語形が似ているだけの別語

ファイル名には検査する語を入れる。固定名にすると、別のセッションが同じ名前で
書いた記事を読んでしまい、指摘が自分のダミーのものだと思い込んだまま判断を誤る。

```bash
probe=/tmp/ai-tone-probe-きちんと.md
cat > "$probe" <<'EOF'
（上の 3 種類を混ぜた 10 行程度の文章）
EOF
~/.config/textlint/lint.sh "$probe"
```

指摘された箇所を実際に読み、「これは直すべきか」を確認する。
直さなくていいものが半分を超えるなら、パターンが広すぎる。
前後の文脈を含めて絞り込むか、そもそも入れないかを選ぶ。

ダミーは検証が終わったら消す（`rm "$probe"`）。`/tmp` に置くのはリポジトリに紛れ込ませないため。

### 4. 規則を書く

書き方は `references/writing-rules.md` にある。**書き始める前に必ず読む。**
prh の正規表現には固有の制約があり、知らずに書くと辞書のロードが失敗する。

### 5. 検証する

実在する記事に当てて、意図した箇所だけが指摘されることを確認する。

```bash
~/.config/textlint/lint.sh <実在する記事の .md>
```

辞書を通すこと自体が prh のロードを兼ねるので、この 1 コマンドが回帰テストになる。
`No rules found` と出たときは指摘が 0 件なのではなく、ルールを読めていない。
`mise install` を通してから実行し直す。

### 6. 誤検出の報告を受けたときは、足すのと同じ手間をかけて外す

辞書は足すほど良くなるものではない。うるさい規則が 1 件あるだけでフック全体が無視されるようになり、
残りの規則も読まれなくなる。**外す判断は足す判断と同じくらい重要**だと考えて扱う。

段階的に弱める。いきなり削除しなくてよい。

1. パターンを絞る（前後の文脈を足して、本当に問題のある形だけを拾う）
2. 規則ごと削除する

どちらの場合も、その語を含む `specs` を絞ったパターンに合わせて書き直す。

### 7. コミットする

コミットメッセージには**なぜその語を足した／外したか**を書く。
半年後に「この規則はなぜあるのか」を判断できるのは、この一行だけになる。

```
feat(textlint): 「〜の第一歩となる」を AI 文体辞書に追加

記事の締めに置かれるが、読者が次に取る操作を何も指定していない。
既存記事 12 本に当てて誤検出なし。
```
