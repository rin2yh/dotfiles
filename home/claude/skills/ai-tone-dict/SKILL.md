# AI 文体辞書の更新

`home/textlint/preset-ja-no-ai-tone` の辞書を育てるスキル。辞書は一度書いて終わりにならない。
使っているうちに「これは誤検出だ」「この言い回しが漏れている」が必ず出てくるので、
そのたびに最小の変更を入れて回帰テストを通す、という作業を繰り返す。

## この辞書の構造を先に把握する

| ファイル | 役割 | `--fix` |
| --- | --- | --- |
| `dict/ai-tone.yml` | 機械的に置換して意味が変わらない規則 | 当てる |
| `dict/ai-tone-review.yml` | 人間の判断が要る規則。`expected` は置換候補ではなく**書き直しの方針** | 当たらない |
| `dict/fix-safety.txt` | `ai-tone.yml` を当てても変わってはいけない文の一覧 | 対象外 |

`scope: chat` は prh が無視する独自キーで、Claude の会話出力を検査する対象に含めるかを示す。
会話は文章より短く砕けているため、文書向けの規則をそのまま当てると誤検出が増える。

分け方を間違えると実害が出る。方針を書いた `expected` を `ai-tone.yml` に置くと、
`--fix` がその方針の文言を本文に埋め込む。迷ったら `ai-tone-review.yml` に置く
（こちらは fixer を登録していないので `--fix` が構造的に届かない）。

## 更新の流れ

### 1. 何を直すのかを一つに絞る

1 回の更新で扱うのは 1 語（とその変種）か、1 件の誤検出まで。
まとめて入れると、後で誤検出が出たときにどの追加が原因か切り分けられなくなる。

入力源は次のどれか。どれであっても、次のステップの判断基準は同じ。

- ユーザーが「この言い回しは AI っぽい」と指摘した
- textlint の指摘が的外れだった（誤検出）
- 書いた文章を読み返して、明らかな常套句が素通りしていた（見逃し）
- フックの指摘がうるさいとフィードバックが来た

### 2. 辞書に入れるべきか判断する

**削除テスト**を当てる。その語を消して文の命題が変わらないなら、
その語は情報を運んでおらず、長さを稼ぐためだけに存在している。辞書に入れてよい。

消すと意味が変わる語は入れない。たとえば `かもしれません` は、
本当に不確実なときに使えば読み手に必要な情報を渡している。
これを一律に禁止すると、根拠のない断定を促すことになって文章が悪くなる。
**不確実性を表す語は、AI っぽく見えることと有害であることが一致しない**ので特に慎重に扱う。

境界線上の語は、`scope: chat` を付けずに `ai-tone-review.yml` へ入れておく。
文書だけで様子を見て、誤検出が出なければ後からチャットに広げる。

### 3. 誤検出の見積もりを取ってから書く

パターンを思いついたら、書く前に手元の文章に当てて何件引っかかるかを見る。

```bash
rg --only-matching --count-matches '<候補パターン>' ~/workspace/**/*.md
```

引っかかった箇所を実際に読み、「これは直すべきか」を数件確認する。
直さなくていいものが半分を超えるなら、パターンが広すぎる。
前後の文脈を含めて絞り込むか、`scope: chat` を外すか、そもそも入れないかを選ぶ。

### 4. 規則を書く

`patterns` と `specs` を必ずセットで書く。prh は `specs` が 1 件でも外れると
辞書のロード自体を失敗させるため、`specs` がそのまま回帰テストになる。

書き方の詳細は `references/writing-rules.md` にある。実際に規則を書く前に必ず読む。
prh の正規表現には固有の制約があり、知らずに書くと辞書のロードが失敗するか、
フック側の網だけが黙って減る。特に次の 2 つは事故が多い。

- 副詞を削る規則の除外文字は、思いついた形ではなく活用の一覧から作る
- `from` と `to` を同じにした `specs` は「この規則にマッチしないこと」の見張りになる

### 5. 検証する

```bash
ai-tone check   # prh のロード、Go の regexp 互換、--fix 安全性、自己コメント
```

**`ai-tone.yml` を触ったら、必ず `--fix` を実際に当てて本文が壊れないか見る。**
この辞書は「無条件に `--fix` して壊れない」約束で運用しており、破ると黙って原稿が壊れる。
`specs` はその規則の中しか検査しないので、規則をまたいだ事故は捕まえられない。

```bash
printf 'この基盤はしっかりした作りだ。\n' > /tmp/probe.md
ai-tone fix /tmp/probe.md && cat /tmp/probe.md
```

壊れる形を見つけたら、直すより先に `dict/fix-safety.txt` へ 1 行足す。
`ai-tone check` がその文を全規則に当てて無変化であることを検査する。
過去に壊した実例は同ファイルのコメントに残してある。

最後に、実際の文章に当てて意図した箇所だけが指摘されることを確認する。

```bash
ai-tone lint <実在する記事の .md>
```

### 6. 誤検出の報告を受けたときは、足すのと同じ手間をかけて外す

辞書は足すほど良くなるものではない。うるさい規則が 1 件あるだけでフック全体が無視されるようになり、
残りの規則も読まれなくなる。**外す判断は足す判断と同じくらい重要**だと考えて扱う。

段階的に弱める。いきなり削除しなくてよい。

1. `scope: chat` を外す（会話では鳴らさず、文書だけで残す）
2. パターンを絞る（前後の文脈を足して、本当に問題のある形だけを拾う）
3. `ai-tone.yml` から `ai-tone-review.yml` へ移す（自動修正をやめて指摘だけにする）
4. 規則ごと削除する

どれを選んだ場合も、その語を含む `specs` を消すか、絞ったパターンに合わせて書き直す。
外した語は `from` と `to` を同じにした `specs` として残す。次に誰かが戻したとき、
同じ議論をやり直す代わりにテストが落ちる。

### 7. コミットする

辞書と（変えたなら）フックを 1 つのコミットにまとめる。
コミットメッセージには**なぜその語を足した／外したか**を書く。
半年後に「この規則はなぜあるのか」を判断できるのは、この一行だけになる。

```
feat(textlint): 「〜の第一歩となる」を AI 文体辞書に追加

記事の締めに置かれるが、読者が次に取る操作を何も指定していない。
既存記事 12 本に当てて誤検出なし。
```

## よくある失敗

| 失敗 | なぜ起きるか |
| --- | --- |
| 一度に語をまとめて追加する | 誤検出が出たとき原因を切り分けられない。1 回の更新は 1 語まで |
| `specs` を書かずに済ませる | パターンが実際には当たっていないことに気づけない。prh のテスト機構を捨てている |
| 方針を書いた `expected` を `ai-tone.yml` に置く | `--fix` が方針の文言を本文に埋め込む |
| `ai-tone.yml` を触って `--fix` を試さない | 述語用法やサ変でない名詞を巻き込んで本文が壊れる。`specs` は規則をまたいだ事故を防げない |
| 除外を `(?!...)` で書く | textlint は解釈するが Go の regexp は受け付けず、会話検査の網だけが減る |
| 誤検出を放置して規則を足し続ける | 警告が信用されなくなり、辞書全体が無視される |
| 不確実性を表す語まで禁止する | 根拠のない断定を促す。AI っぽさと文章の悪さは別物 |
