# AI 文体辞書の更新

`home/textlint/preset-ja-no-ai-tone` の辞書を育てるスキル。辞書は一度書いて終わりにならない。
使っているうちに「これは誤検出だ」「この言い回しが漏れている」が必ず出てくるので、
そのたびに最小の変更を入れて回帰テストを通す、という作業を繰り返す。

## この辞書の構造を先に把握する

| ファイル | 役割 | `--fix` |
| --- | --- | --- |
| `dict/ai-tone.yml` | 機械的に置換して意味が変わらない規則 | 当てる |
| `dict/ai-tone-review.yml` | 人間の判断が要る規則。`expected` は置換候補ではなく**書き直しの方針** | 当てない |
| `dict/fix-safety.txt` | `ai-tone.yml` を当てても変わってはいけない文の一覧 | 対象外 |
| `dict/generated/*.patterns` | 上記から生成した ripgrep 用パターン。Stop フックが使う | 対象外 |

`scope: chat` は prh が無視する独自キーで、Claude の会話出力を検査する対象に含めるかを示す。
会話は文章より短く砕けているため、文書向けの規則をそのまま当てると誤検出が増える。

分け方を間違えると実害が出る。方針を書いた `expected` を `ai-tone.yml` に置くと、
`--fix` がその方針の文言を本文に埋め込む。迷ったら `ai-tone-review.yml` に置く。

## 更新の流れ

### 1. 何を直すのかを一つに絞る

1 回の更新で扱うのは 1 語（とその変種）か、1 件の誤検出まで。
まとめて入れると、後で誤検出が出たときにどの追加が原因か切り分けられなくなる。

入力源は次のどれか。どれであっても、次のステップの判断基準は同じ。

- ユーザーが「この言い回しは AI っぽい」と指摘した
- textlint の指摘が的外れだった（誤検出）
- 書いた文章を読み返して、明らかな常套句が素通りしていた（見逃し）
- フックの警告がうるさい、または弱すぎるとフィードバックが来た

### 2. 辞書に入れるべきか判断する

**削除テスト**を当てる。その語を消して文の命題が変わらないなら、
その語は情報を運んでおらず、長さを稼ぐためだけに存在している。辞書に入れてよい。

消すと意味が変わる語は入れない。たとえば `かもしれません` は、
本当に不確実なときに使えば読み手に必要な情報を渡している。
これを一律に禁止すると、根拠のない断定を促すことになって文章が悪くなる。
**不確実性を表す語は、AI っぽく見えることと有害であることが一致しない**ので特に慎重に扱う。

境界線上の語は、`scope: chat` を付けずに `ai-tone-review.yml` へ入れておく。
文書だけで様子を見て、誤検出が出なければ後からチャットに広げる。

### 3. 誤検出の見積もりを取ってから書く

パターンを思いついたら、書く前に手元の文章に当てて何件引っかかるかを見る。

```bash
rg --only-matching --count-matches '<候補パターン>' ~/workspace/**/*.md
```

引っかかった箇所を実際に読み、「これは直すべきか」を数件確認する。
直さなくていいものが半分を超えるなら、パターンが広すぎる。
前後の文脈を含めて絞り込むか、`scope: chat` を外すか、そもそも入れないかを選ぶ。

### 4. 規則を書く

`patterns` と `specs` を必ずセットで書く。prh は `specs` が 1 件でも外れると
辞書のロード自体を失敗させるため、`specs` がそのまま回帰テストになる。
書いたつもりのパターンが実際にはマッチしていない、という一番ありがちな失敗をここで潰せる。

```yaml
  - expected: 数を書くか列挙する
    scope: chat
    patterns:
      - 様々な
      - さまざまな
    specs:
      - from: 様々な要因がある
        to: 数を書くか列挙する要因がある
```

`ai-tone-review.yml` では `expected` が本文に差し込まれた文字列が `to` になる。
日本語として不自然に見えるが、これは `--fix` を当てない辞書なので問題ない。
`specs` の役目はパターンが当たることの確認であって、出力の自然さではない。

**`from` と `to` を同じにした `specs` は「この規則にマッチしないこと」の表明として使える。**
判断して外した語をここに残しておけば、戻そうとした人の手元で `npm test` が落ちる。
「なぜ入れなかったか」をコメントで説明するより、テストで守るほうが強い。

```yaml
    specs:
      - from: 様々な要因がある
        to: 数を書くか列挙する要因がある
      - from: 幅広い層に使われている      # 外した語。戻すとここで落ちる
        to: 幅広い層に使われている
```

prh の正規表現には制約がある。踏むと辞書のロードが失敗するので先に知っておく。

- リテラルに使えるフラグは `gimy` だけ。`/.../u` と書くと正規表現として認識されず、
  文字列リテラルとして丸ごとエスケープされる
- `u` フラグが常に付与されるため、`\u{...}` とサロゲートペアが書けない。
  絵文字のような文字は実物を `patterns` に列挙する
- prh が見るのは Markdown の記法を取り除いた本文。`^#` のような記法依存の判定はできない
- 後方参照は `$1` 形式（`\1` ではない）。prh は複数の `patterns` を 1 本の選択に畳むため
  グループ番号がずれる。後方参照を使う規則は 1 パターンずつ別の規則に分ける
- **ripgrep には先読みが無い。** `(?!...)` を書くと textlint では効くが生成物からは黙って落ち、
  フック側の網だけが減る。除外したいときは「後続の 1 文字を捕まえて `$1` で書き戻す」形にする

```yaml
  # 「しっかりした」を巻き込まずに「しっかり検証する」だけを削る書き方
  - expected: $1
    pattern: /しっかり([^しと])/
```

### 5. 検証する

```bash
cd ~/workspace/dotfiles/home/textlint
npm run gen   # 辞書 → ripgrep パターンの再生成
npm test      # prh のロード、生成物の同期、ripgrep 構文、--fix 安全性
```

`npm run gen` を忘れると、textlint は新しい規則で動くのにフックだけ古い規則で動く、
という気づきにくいずれが起きる。`npm test` がこのずれを検出するので、
テストが落ちたらまず `npm run gen` を実行したか確認する。

**`ai-tone.yml` を触ったら、必ず `--fix` を実際に当てて本文が壊れないか見る。**
この辞書は「無条件に `--fix` して壊れない」約束で運用しており、破ると黙って原稿が壊れる。
`specs` はその規則の中でしか効かないので、規則をまたいだ事故は捕まえられない。

```bash
printf 'この基盤はしっかりした作りだ。\n' > /tmp/probe.md
npm run fix -- /tmp/probe.md && cat /tmp/probe.md
```

壊れる形を見つけたら、直すより先に `dict/fix-safety.txt` へ 1 行足す。
`npm test` がその文を全規則に当てて無変化であることを検査するので、次からは自動で止まる。
実例: `しっかり` を裸で拾っていた頃は「しっかりした作り」が「した作り」になっていた。
`〜を行う` を任意の漢字 2 文字以上で拾うと「儀式を行う」が「儀式する」になる。
どちらも `--fix` を一度当てていれば書く前に気づけた。

生成物 (`dict/generated/`) もコミット対象。フックは `npm install` 前でも動く必要があるため、
ビルド成果物だがリポジトリに入れてある。

最後に、実際の文章に当てて意図した箇所だけが指摘されることを確認する。

```bash
npx textlint --format compact <実在する記事の .md>
```

### 6. 誤検出の報告を受けたときは、足すのと同じ手間をかけて外す

辞書は足すほど良くなるものではない。うるさい規則が 1 件あるだけでフック全体が無視されるようになり、
残りの規則も効かなくなる。**外す判断は足す判断と同じくらい重要**だと考えて扱う。

段階的に弱める。いきなり削除しなくてよい。

1. `scope: chat` を外す（会話では鳴らさず、文書だけで残す）
2. パターンを絞る（前後の文脈を足して、本当に問題のある形だけを拾う）
3. `ai-tone.yml` から `ai-tone-review.yml` へ移す（自動修正をやめて指摘だけにする）
4. 規則ごと削除する

どれを選んだ場合も、その語を含む `specs` を消すか、絞ったパターンに合わせて書き直す。
外した語は `from` と `to` を同じにした `specs` として残す。次に誰かが戻したとき、
同じ議論をやり直す代わりにテストが落ちる。

### 7. コミットする

辞書・生成物・（変えたなら）フックを 1 つのコミットにまとめる。
コミットメッセージには**なぜその語を足した／外したか**を書く。
半年後に「この規則はなぜあるのか」を判断できるのは、この一行だけになる。

```
feat(textlint): 「〜の第一歩となる」を AI 文体辞書に追加

記事の締めに置かれるが、読者が次に取る操作を何も指定していない。
既存記事 12 本に当てて誤検出なし。
```

## 強度の切り替えはコードを触らずに行う

フックの強さは環境変数で決まる。「うるさい」「効いていない」と言われたときに
まず検討するのはこちらで、辞書をいじるのはその後。

| 変数 | 既定 | 意味 |
| --- | --- | --- |
| `CLAUDE_AI_TONE_CHAT` | `warn` | 会話出力。`off` / `warn`（警告のみ）/ `block`（応答をやり直させる） |
| `CLAUDE_AI_TONE_FILE` | `block` | Markdown 書き込み時。`off` / `warn` / `block` |

記事を書くセッションだけ `CLAUDE_AI_TONE_CHAT=block` にする、といった使い分けを想定している。

## よくある失敗

| 失敗 | なぜ起きるか |
| --- | --- |
| 一度に語をまとめて追加する | 誤検出が出たとき原因を切り分けられない。1 回の更新は 1 語まで |
| `specs` を書かずに済ませる | パターンが実際には当たっていないことに気づけない。prh のテスト機構を捨てている |
| `npm run gen` を忘れる | textlint とフックが別の規則で動く。`npm test` が落ちるので必ず確認する |
| 方針を書いた `expected` を `ai-tone.yml` に置く | `--fix` が方針の文言を本文に埋め込む |
| `ai-tone.yml` を触って `--fix` を試さない | 述語用法やサ変でない名詞を巻き込んで本文が壊れる。`specs` は規則をまたいだ事故を防げない |
| 除外を `(?!...)` で書く | textlint では効くが ripgrep の生成物からは黙って落ち、フックの網だけが減る |
| 誤検出を放置して規則を足し続ける | 警告が信用されなくなり、辞書全体が無視される |
| 不確実性を表す語まで禁止する | 根拠のない断定を促す。AI っぽさと文章の悪さは別物 |
